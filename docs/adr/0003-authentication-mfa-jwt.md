# ADR-0003: 사번·비밀번호 + TOTP MFA + JWT·refresh 회전

- 상태: 제안
- 날짜: 2026-10-21
- 상세: [authentication.md](../03-security/authentication.md)

## 배경

ERP에는 계약 금액이나 개인정보 같은 민감한 데이터가 있습니다. 데스크톱과 웹 클라이언트가 같은 API를 씁니다. 설치형이라 외부 IdP(Entra ID 등)가 없는 고객사도 있습니다.

## 결정

- 1차 인증은 사번과 비밀번호, 2차 인증은 TOTP로 합니다. **MFA는 필수**입니다.
- 1차 인증을 통과하면 MFA 전용 단기 토큰(`mfaToken`)만 발급하고, MFA까지 통과해야 JWT를 발급합니다.
- access 토큰은 수명 15분짜리 ES256 JWT입니다. refresh 토큰은 무작위 값이고, 사용할 때마다 회전하며 재사용을 탐지합니다.
- refresh 토큰 저장: Desktop은 DPAPI로 암호화해서 보관하고, Web은 HttpOnly 쿠키에 둡니다.
- 사용자 저장소, 비밀번호 해시, 계정 잠금에는 ASP.NET Core Identity Core를 씁니다. 토큰 발급은 직접 구현합니다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **직접 발급하는 JWT + Identity Core** | 의존성이 적음. 설치형에 적합. 흐름을 완전히 통제할 수 있음 | 토큰 보안을 직접 책임져야 함 |
| OpenIddict 같은 OIDC 서버 내장 | 표준 프로토콜. 나중에 SSO로 확장 가능 | 설정이 복잡함. 지금 요구사항(1st-party 클라이언트만 있음)에는 과함 |
| 외부 IdP (Entra ID, Keycloak) | 보안 책임을 넘길 수 있음 | 설치형 고객사에 추가 인프라가 필요함. 사번 로그인 요구와 맞지 않음 |
| 세션 쿠키만 사용 | 단순함 | 데스크톱 클라이언트에 맞지 않음 |

## 결과

- 외부 IdP 연동(SSO)은 나중에 OIDC 로그인을 추가하는 방식으로 확장할 수 있습니다. 토큰 발급 구조는 그대로 둡니다.
- TOTP 코드 재사용 방지와 비밀키 암호화가 Identity 기본 기능만으로 충분한지 확인이 필요합니다 (미결 사항 Q11).
